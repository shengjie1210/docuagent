> 文档版本：V1.0
> 编写日期：2026-10-20
> 阶段：瀑布模型 · 第一步 需求分析

---

## 1. 引言

### 1.1 编写目的
本文档定义 DocuAgent 智能文档管理助手的功能需求、非功能需求和外部接口需求，作为后续概要设计、详细设计、编码和测试的基准。预期读者：开发人员、测试人员、项目负责人。

### 1.2 项目背景
随着个人和团队文档数量增长，传统文件夹管理方式存在检索困难、摘要缺失、分类混乱等问题。本项目利用大语言模型（LLM）+ RAG 检索增强 + Function Call 工具调用技术，构建一个能"读懂文档、回答问题、主动整理"的智能文档管理系统。

### 1.3 产品定位
- **目标用户**：需要管理大量文档（PDF/Word/Markdown/TXT）的个人知识工作者、学生、小型团队。
- **核心价值**：上传文档后，用户用自然语言提问或下达指令，AI 基于文档内容回答并执行整理操作，无需手动翻找和总结。
- **不做什么**：不做多人协作编辑、不做在线 Office 编辑、不做文档版本控制（V1 不实现，预留扩展）。

### 1.4 术语定义
| 术语 | 说明 |
|---|---|
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| Embedding | 将文本转换为向量的过程 |
| Chunk | 文档切分后的文本块 |
| Function Call | 大模型调用外部工具的能力 |
| SSE | Server-Sent Events，服务器推送事件，用于流式输出 |
| VectorStore | 向量数据库/向量存储 |

## 2. 总体描述

### 2.1 产品愿景
让文档管理从"人找文档"变成"文档找人"——用户用自然语言描述需求，Agent 自动检索、总结、归类。

### 2.2 用户角色
| 角色 | 描述 |
|---|---|
| 普通用户 | 注册后可上传自己的文档、与 AI 对话、管理个人文档 |
| 系统管理员 | V1 不实现后台管理，默认单用户场景 |

### 2.3 运行环境
- **后端**：JDK 21、Spring Boot 3\.x、MySQL 8.x、Redis 7.x
- **前端**：现代浏览器（Chrome/Edge）、Node.js 18+
- **外部服务**：阿里云百炼 DashScope API（通义千问 + Embedding 模型）

### 2.4 设计与实现约束
- 后端必须使用 Spring AI 框架接入大模型（ChatClient、VectorStore、Tool Callback）
- 向量存储 V1 采用 Spring AI 内置 SimpleVectorStore（文件持久化），不引入独立向量数据库
- 认证使用 JWT，不使用 Session
- 前端使用 Vue 3 + Element Plus
- API Key 等敏感信息通过环境变量注入，不硬编码

## 3. 功能需求

### 3.1 用户认证模块（AUTH）

| 编号 | 需求 | 优先级 |
|---|---|---|
| AUTH-01 | 用户可通过用户名+密码注册，密码加密存储（BCrypt） | 高 |
| AUTH-02 | 已注册用户可登录，登录成功返回 JWT Token | 高 |
| AUTH-03 | 除登录/注册接口外，所有接口必须携带有效 JWT | 高 |
| AUTH-04 | JWT 过期时间 2 小时，过期后需重新登录 | 中 |
| AUTH-05 | 用户只能访问自己上传的文档和对话，数据隔离 | 高 |

### 3.2 文档管理模块（DOC）

| 编号 | 需求 | 优先级 |
|---|---|---|
| DOC-01 | 用户可上传 PDF / DOCX / MD / TXT 格式文档 | 高 |
| DOC-02 | 单文件大小限制 20MB | 高 |
| DOC-03 | 上传后系统自动解析文本内容、切分 chunk、生成向量并入库 | 高 |
| DOC-04 | 上传完成后自动调用大模型生成文档摘要（100-200字） | 中 |
| DOC-05 | 用户可查看自己的文档列表（文件名、类型、大小、上传时间、摘要、标签） | 高 |
| DOC-06 | 用户可按文件名关键词搜索文档 | 中 |
| DOC-07 | 用户可删除文档（同时删除向量数据和文件） | 高 |
| DOC-08 | 用户可查看文档原文预览（纯文本提取后） | 中 |

### 3.3 RAG 对话模块（CHAT）

| 编号 | 需求 | 优先级 |
|---|---|---|
| CHAT-01 | 用户可创建新对话会话，会话标题自动取首条消息前 20 字 | 高 |
| CHAT-02 | 用户可查看历史对话列表、切换对话、删除对话 | 高 |
| CHAT-03 | 用户在对话中输入问题，系统基于该用户的文档向量库检索 top-5 相关片段 | 高 |
| CHAT-04 | 检索到的片段拼入 prompt，大模型基于片段回答，不允许编造 | 高 |
| CHAT-05 | 回答以 SSE 流式输出，前端逐字显示 | 高 |
| CHAT-06 | 回答下方展示引用来源（文档名 + 片段摘要），用户可点击查看原文 | 高 |
| CHAT-07 | 系统保留最近 10 轮对话上下文，实现多轮记忆 | 高 |
| CHAT-08 | 上下文超过 10 轮时，最早的消息截断 | 中 |
| CHAT-09 | 若检索无相关片段，系统明确回复"未在您的文档中找到相关信息" | 高 |

### 3.4 Agent 工具调用模块（AGENT）

| 编号 | 需求 | 优先级 |
|---|---|---|
| AGENT-01 | 大模型可根据用户意图自动调用以下工具 | 高 |
| AGENT-02 | 工具 `search_documents(keyword)`：按关键词搜索用户文档列表 | 高 |
| AGENT-03 | 工具 `summarize_document(docId)`：对指定文档生成摘要 | 中 |
| AGENT-04 | 工具 `list_recent_documents(limit)`：列出最近上传的 N 篇文档 | 中 |
| AGENT-05 | 工具 `search_in_document(docId, keyword)`：在指定文档内搜索关键词 | 低 |
| AGENT-06 | 工具调用过程对用户透明，最终返回自然语言结果 | 高 |
| AGENT-07 | 工具执行出错时，错误信息回传给模型，模型向用户解释并引导重试 | 中 |

### 3.5 前端页面

| 编号 | 页面 | 需求 |
|---|---|---|
| UI-01 | 登录/注册页 | 用户名密码输入，切换登录/注册 |
| UI-02 | 主布局 | 左侧边栏（对话列表 / 文档管理 tab 切换），右侧主内容区 |
| UI-03 | 文档管理页 | 上传按钮、文档表格（文件名/类型/大小/摘要/标签/操作）、删除确认 |
| UI-04 | 对话页 | 消息气泡列表、输入框、流式输出光标、引用来源卡片 |
| UI-05 | 响应式 | 最小支持 1280px 宽度，V1 不做移动端适配 |

## 4. 外部接口需求

### 4.1 用户界面
- 遵循 Element Plus 组件库风格
- 主色调用蓝色系，简洁专业

### 4.2 软件接口
| 接口 | 用途 |
|---|---|
| 阿里云百炼 DashScope Chat API | 大模型对话生成（qwen-plus） |
| 阿里云百炼 DashScope Embedding API | 文本向量化（text-embedding-v3） |
| MySQL 8.x | 存储用户、文档元数据、对话记录 |
| Redis 7.x | 存储 JWT 黑名单、对话上下文缓存 |

### 4.3 通信接口
- 前端通过 HTTPS/WSS 与后端通信（开发环境 HTTP）
- 后端通过 HTTPS 调用 DashScope API
- SSE 使用 text/event-stream 协议

## 5. 非功能需求

### 5.1 性能需求
| 指标 | 要求 |
|---|---|
| 首字响应时间（TTFT） | < 3 秒（含检索 + 模型首 token） |
| 文档上传解析（10MB PDF） | < 10 秒完成切分入库 |
| 并发用户数 | 支持 50 人同时在线（单用户场景足够） |
| 单文档向量检索响应 | < 500ms |

### 5.2 安全需求
- 密码 BCrypt 加密存储，不可逆
- JWT 密钥从环境变量读取
- 用户 A 无法通过 API 参数遍历访问用户 B 的文档（数据隔离校验）
- 上传文件类型白名单校验，防止可执行文件上传
- 文件存储路径不可被直接遍历下载（需鉴权）

### 5.3 可用性需求
- 系统可用性 99%（个人项目，非生产级）
- 前端操作无需培训即可上手
- API 返回统一 JSON 格式：`{ code, message, data }`

### 5.4 可维护性
- 后端按 Controller/Service/Mapper 分层
- 配置项集中在 application.yml
- 关键逻辑有中文注释
- Git 提交信息遵循 conventional commits（feat/fix/docs 等）

## 6. 数据需求概要

### 6.1 数据实体
- 用户（User）
- 文档（Document）
- 对话（Conversation）
- 消息（Message）
- 向量数据（由 VectorStore 管理，关系型数据库不存）

### 6.2 数据保留
- 用户删除账号后，其文档和对话级联删除
- 对话记录永久保留（V1）
- 上传的原始文件在文档删除时一并删除

## 7. 验收标准

### 7.1 功能验收
1. 新用户注册 -> 登录 -> 获得 Token
2. 上传一份 TXT/MD 文档 -> 列表可见 -> 摘要自动生成
3. 在对话中提问文档相关问题 -> AI 基于文档回答 -> 显示引用来源
4. 问文档无关问题 -> AI 回复"未在文档中找到"
5. 说"帮我总结最近上传的文档" -> AI 自动调用 summarize 工具 -> 返回摘要
6. 多轮对话中追问"那第二篇呢" -> AI 能理解上下文
7. 删除文档 -> 列表和向量数据同步消失
